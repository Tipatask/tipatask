## CLAUDE.md Overlay

### Project Approach: Greenfield (Original Specification)

This project starts from an "Original Specification" — the goal is to define the full spec before writing any implementation, and the spec comes from the user, not from assumptions. The project folder may still hold pre-existing code (an old prototype, a vendored backend, a half-built module); that is checked first, before any spec question is asked.

**Mandatory sequencing:**
1. Scan for pre-existing code first. The `Scan for pre-existing code` starter task lists the project root and one level deep (skipping `node_modules`/`dist`/`build`/`.git`/`vendor` and the Tipatask-owned `ai`/`.tipatask`/`.claude`/`.codex`) and creates one `Inspect existing code: {folder}` CODING task per folder that holds source files or a manifest. It then adds those keys to the `dependencies` of all four spec starter tasks — which are seeded already depending on the scan task, so none of them can even be started before it finishes.
2. Each inspection task asks the user in objective-chat, in batches of 3-5 questions, what that codebase is and what it should be used for, records the answer under `## Existing Code` in `ai/architecture/GENERAL.md`, and spawns `Investigate {folder}/{module}` follow-up tasks tagged with the relevant `tt-*` module tags.
3. Interrogate the user in objective-chat for the missing details of each spec area (architecture, data model, user flows, tech stack) — ask, don't guess.
4. Scan the project root for existing `*.md`/`*.txt`/`*.pdf` files and confirm with the user whether each counts as project documentation; read the confirmed ones as source of truth.
5. Write each of the four spec sections into `ai/architecture/GENERAL.md`: architecture (components, boundaries, data flow), data model (entities, relations, key fields), core user flows (primary journeys end-to-end), tech stack (language, framework, DB, deploy target — with rationale).
6. `Choose tech stack` runs last, not alongside the other three. It depends on `Draft initial system architecture`, `Define data model and schema`, and `Identify core user flows` and is seeded one sprint after them — the board will not let it start until all three are `completed`. A stack is picked only once what is being built is known.
7. Backlog generation: `Choose tech stack` is the final spec task by construction (see 6), so when it completes it re-reads the assembled spec (including `## Existing Code`) and generates the real build-task backlog via `create_task` — every backlog task depends on the inspection/investigate tasks and carries the `preset-a-backlog` tag.
8. Begin implementation tasks only after the build backlog has been generated in step 7 — not before.

**Discovery rules:**
- Never assume the project is empty — read `## Existing Code` in `GENERAL.md` before asking spec questions.
- Never invent a spec answer — ask the user, in batches of 3-5 questions, and follow up on vague replies.
- If the user says "you decide", record it as an explicit **Assumption** line in the spec section instead of silently choosing.
- Treat user-confirmed `*.md`/`*.txt`/`*.pdf` files as source of truth over inference; unconfirmed files are ignored.

**What to AVOID:**
- Writing any spec section before the code-scan task and its inspection tasks are `completed`.
- Treating `ai/`, `.tipatask/`, `.claude/`, or `.codex/` as the user's pre-existing code — Tipatask created them.
- Writing production code before architecture and data model tasks are `completed`.
- Writing a spec section without asking the user anything first.
- Ignoring documentation files sitting in the project root.
- Picking a tech stack before requirements are defined.
- Inventing schema details that should come from spec tasks.
- Creating build/implementation tasks before all four starter tasks are `completed` and the gate has run.

**When implementing:**
- Each implementation task must reference at least one completed spec task.
- Do not design for hypothetical future requirements — implement only what the spec tasks describe.
- Build tasks are generated by the completion gate (step 6 above), not hand-written ad hoc.
