## CLAUDE.md Overlay

### Project Approach: Existing Codebase Discovery

This project's folder already holds code — that code is the foundation to build on, not scaffolding to discard. The goal is to understand what is there and what the user wants next before writing anything.

**Mandatory sequencing:**
1. `Map the existing codebase` — lists the project root and one level deep (skipping `node_modules`/`dist`/`build`/`.git`/`vendor` and the Tipatask-owned `ai`/`.tipatask`/`.claude`/`.codex`) and creates one `Inspect existing code: {folder}` CODING task per folder holding source files or a manifest. It then adds those keys to the `dependencies` of the four sprint-2 documentation tasks and the KB-discovery task — none of them can start before it finishes (they are seeded already depending on it).
2. Each inspection task asks the user in objective-chat, in batches of 3-5 questions, what that folder is and whether it is kept/extended/replaced, and records the answer under `## Existing Code` in `ai/architecture/GENERAL.md`.
3. `Profile the project with the user` (also sprint 1) interviews the user about the product, its users, and what comes next — this is what used to be the wizard's Description step. From the answers it decides which of three conditional tracks apply (`legacy` — migrating off this code; `frontend` — a frontend surface needs an API contract/state strategy; `backend` — a backend surface needs endpoint mapping/integration design) and records them under `## Project Profile` → `### Recommended Tracks`. None, one, or several may apply.
4. The four sprint-2 documentation tasks read the code first (not the other way around) and only ask the user what the code cannot answer — near-term direction, planned changes, constraints. Each writes one section of `ai/architecture/GENERAL.md`: architecture (components that exist today, boundaries, data flow), data model (real entities/relations from the schema), core user flows (journeys the code already supports, plus planned ones marked `(planned)`), and stack/commands/env (from real manifests and config).
5. Completion gate: once all four documentation tasks are `completed`, the last one to finish re-reads the assembled `GENERAL.md` (including `## Existing Code` and `## Project Profile`), expands the recommended tracks' items into a real backlog alongside anything else the docs and the user's goals call for, proposes it to the user, and on approval calls `create_task` once per item — every backlog task depends on the inspection/investigate tasks and carries the `preset-b-backlog` tag.
6. Begin implementation tasks only after the build backlog has been generated by the gate — not before.

**Discovery rules:**
- Never guess what a folder is for — ask the user. Never guess project direction — ask the user.
- Treat the existing code as the project's foundation by default; only the `legacy` track (chosen during profiling, not assumed) treats it as something to migrate off.
- If the user says "you decide", record it as an explicit **Assumption** line instead of silently choosing.
- Prefer what the code actually does over what any stale README claims — note discrepancies instead of trusting docs blindly.

**What to AVOID:**
- Writing any documentation section before `Map the existing codebase` and its inspection tasks are `completed`.
- Treating `ai/`, `.tipatask/`, `.claude/`, or `.codex/` as the user's pre-existing code — Tipatask created them.
- Assuming a legacy-refactor, frontend, or backend track applies without the profile task's answers calling for it.
- Writing production code before the documentation tasks and the completion gate have run.
- Inventing schema, endpoint, or flow details the code and the user haven't confirmed.

**When implementing:**
- Each implementation task must reference at least one completed documentation task.
- Do not design for hypothetical future requirements beyond what the profile task recorded.
- Build tasks are generated by the completion gate, not hand-written ad hoc.
